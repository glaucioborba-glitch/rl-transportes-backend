================================================================================
1. RESUMO EXECUTIVO
================================================================================

O projeto é um monorepo maduro, com dezenas de módulos NestJS (fases 1–22) e um frontend
Next.js amplo (portal cliente, staff/intranet, operador, cockpit, BI/GRC/demo). O núcleo
operacional recente — Solicitações v2 → Gate-v2 → Pátio-v2 → Timeline 360 → Motor de
Armazenagem — está bem encaminhado, com transações Prisma, tenant isolation no portal e
padrão outbox para integrações assíncronas.

Os maiores riscos para produção são:

  (A) Duas trilhas paralelas de operação/faturamento (Gate-v2 vs TOS) sem fronteira clara.
  (B) Sessão do portal cliente apenas em memória (perde login ao recarregar a página).
  (C) Outbox sem lock de concorrência (risco de processamento duplicado com múltiplas instâncias).
  (D) Middleware Next.js não protege /portal/* no servidor (só redirect client-side).
  (E) Dev local frágil no Windows (scripts bash-only; defaults de porta inconsistentes).

Estimativa de esforço para “production-ready” no núcleo operacional: 3–5 sprints focados,
sem contar hardening completo de todos os módulos “Fase N” demo.

3. CRÍTICO — CORRIGIR ANTES DE PRODUÇÃO
================================================================================

[C1] Sessão portal cliente volátil (memória only)
------------------------------------------------------------------
Arquivo: apps/web/stores/portalClienteAuthStore.ts (linha 5: "Tokens só em memória")
Problema: accessToken e refreshToken somem ao F5/nova aba. UX ruim; risco de workarounds inseguros
          (localStorage sem criptografia, tokens em query string, etc.).
Correção sugerida:
  - Opção A (recomendada): BFF Next com HttpOnly cookies para refresh (espelhar padrão staff em
    apps/web/app/api/auth/*).
  - Opção B: sessionStorage criptografado + refresh automático no layout (menos seguro que HttpOnly).
  - Garantir rotação de refresh token e revogação alinhada ao tokenVersion do backend.
Critério de aceite: F5 em /portal/dashboard mantém sessão; logout invalida cookie.

[C2] Outbox sem controle de concorrência
------------------------------------------------------------------
Arquivo: apps/backend/src/outbox/outbox.service.ts (claimPending: findMany simples, linhas 21–26)
Problema: duas instâncias Nest podem processar o mesmo evento → NFS-e/boleto/faturamento duplicado.
Correção sugerida:
  - Adicionar status PROCESSING + claim atômico (UPDATE … WHERE status=PENDING RETURNING * ou
    SELECT … FOR UPDATE SKIP LOCKED via $queryRaw).
  - Retry com backoff para FAILED (max attempts + dead letter).
  - Manter idempotência por outboxId nos processors (já parcialmente feito em billing e nfse-boleto).
Critério de aceite: teste com 2 workers paralelos processando 100 eventos → 0 duplicatas.

[C3] Dupla trilha de faturamento (Gate-v2 vs TOS)
------------------------------------------------------------------
Arquivos:
  - Gate-v2: armazenagem-billing.service.ts → PreFatura/Fatura → EMITIR_NFSE_BOLETO
  - TOS: container-lifecycle → BILLING_TRIGGERED → billing-outbox.processor.ts
Problema: mesmo contêiner físico pode acionar dois motores de cobrança com regras diferentes.
Correção sugerida:
  - Definir DONO único por tipo de operação (documentar matriz decisão).
  - Gate-v2/solicitação corporativa → PreFatura (novo motor).
  - TOS/agendamento depot puro → outbox BILLING_TRIGGERED (legado) OU unificar em serviço único.
  - Adicionar guard: antes de criar Fatura/PreFatura, verificar se já existe cobrança TOS para ISO+período.
  - Teste e2e: gate-in → dias → gate-out → exatamente 1 fatura, 1 NFS-e, 1 boleto.
Critério de aceite: matriz publicada no README + teste anti double-charge verde.

[C4] Upload de fotos gate fora da transação
------------------------------------------------------------------
Arquivo: apps/backend/src/gate-v2/gate.service.ts (~250–316)
Problema: arquivos persistidos em storage antes do $transaction; rollback deixa órfãos S3/local.
Correção sugerida:
  - Padrão saga: gravar em path temporário, commit TX, depois mover/promover arquivos; ou
  - Job de limpeza de órfãos + compensação on failure.
Critério de aceite: falha simulada no meio do check-in não deixa lixo permanente.

[C5] Portal /portal/* sem guard no middleware
------------------------------------------------------------------
Arquivo: apps/web/middleware.ts — protege staff e motorista, NÃO /portal/*
          apps/web/components/portal/portal-shell.tsx (linhas 59–62) — redirect client-side only
Problema: rotas portal renderizam HTML/JS antes do redirect; possível flash de conteúdo; SEO/crawler;
          APIs chamadas antes do shell montar.
Correção sugerida:
  - Estender middleware com lista de rotas públicas portal (/portal/login, cadastrar, recuperar…)
    e validar cookie/JWT portal via BFF /api/portal/me (similar a /api/auth/me).
Critério de aceite: request direto a /portal/dashboard sem sessão → 302 antes de render.

[C6] Defaults de porta inconsistentes
------------------------------------------------------------------
Arquivos:
  - apps/backend/src/main.ts:408 → default API_PORT '3000'
  - .env.example / docs / credenciais → 3001
  - apps/backend/prisma.config.ts:12 → fallback DB porta 5432
  - docker-compose.yml → Postgres host 5433
Problema: dev quebrado silenciosamente (API na porta errada; migrate no DB errado).
Correção sugerida:
  - main.ts default → 3001
  - prisma.config.ts fallback → 5433 e DB rl (alinhar compose) OU remover fallback hardcoded
  - Validar no bootstrap: log claro de DATABASE_URL host:porta
Critério de aceite: clone fresh + docker compose up + npm run dev:all funciona sem .env custom.

[H1] Scripts dev Windows

  - Criar scripts/start-all.ps1 e npm run dev:all:win ou usar concurrently cross-platform.

  Criar apps/backend/test/gate-v2.e2e-spec.ts mínimo (check-in → check-out → pré-fatura consolidada).

[H3] Testes unitários de serviços críticos
  Existem specs util/outbox parcial; faltam:
  - ArmazenagemBillingService (openPreFaturas, consolidateOnGateOut)
  - ContainerTimelineService (tenant isolation)
  - AgendamentosService
  - OutboxWorker (routing de event types)

[H4] AppModule monolítico (65+ imports)
  - apps/backend/src/app.module.ts carrega TODOS os módulos “Fase N” no boot.
  - Agrupar: CoreOperacionalModule | CxPortaisModule | PlatformExtensionsModule.
  - Feature flag FEATURE_PHASES=0 para deploy lean (só operacional + portal).

[H5] Stores CX em memória
  - portal-fornecedor-identities.store.ts, tickets, branding, plataforma-api-client.store.ts
  - Perdidos no restart; não escalam horizontalmente.
  - Persistir em Prisma ou marcar @deprecated + desabilitar em prod.

[H6] Rate limit portal in-process
  - cx-portal-rate-limit.service.ts: Map local.
  - Migrar para Redis (já disponível) com chave por IP/documento/rota.

[H7] Redis opcional em dev/prod
  - REDIS_OPTIONAL=1 permite fallback memória → sessão/brute-force inconsistente entre instâncias.
  - Produção: REDIS_OPTIONAL=0, fail-closed se Redis indisponível.

[H8] CSRF desligado por default
  - .env.example CSRF_ENABLED=0; habilitar em prod com NEXT_PUBLIC_CSRF_ENABLED alinhado.

[H9] NfseBoletoOutboxProcessor — placeholder dev
  - apps/backend/src/outbox/nfse-boleto-outbox.processor.ts cria NFS-e/boleto mock.
  - Antes de prod: integrar NfseService real + idempotência IPM; não gerar numeroNfe fake.

[H10] portal-client.ts monolítico (~1500 linhas)
  - Dividir: portal-auth-client, portal-solicitacoes-client, portal-financeiro-client, portal-container-client.
  - Facilita testes e ownership.

7. ARQUITETURA — RECOMENDAÇÕES ESTRUTURAIS
================================================================================

Estado alvo recomendado:

  ┌─────────────────────────────────────────────────────────────┐
  │                    MODULAR MONOLITH                          │
  ├─────────────────┬─────────────────┬───────────────────────────┤
  │  operacional/   │  cx/            │  platform/ (opcional)     │
  │  solicitacoes-v2│  portais        │  fases demo / BI / GRC    │
  │  gate-v2        │  identity       │  feature-flag off prod    │
  │  patio-v2       │  dashboard      │                           │
  │  agendamentos   │  pessoas-auth   │                           │
  │  dispatch       │                 │                           │
  │  container-tl   │                 │                           │
  │  armazenagem    │                 │                           │
  └─────────────────┴─────────────────┴───────────────────────────┘

Princípios:
  1. Um aggregate writer por concern (não duplicar billing Gate + TOS).
  2. Outbox único com claim atômico + idempotência em todos processors.
  3. Read models (timeline, dashboard) agregam múltiplas fontes — OK, mas writes devem ser únicos.
  4. Portal BFF (Next /api) esconde tokens do browser — alinhar staff e cliente.
  5. Bounded context imports: operacional NÃO importa platform extensions.

Fluxo billing unificado (proposta):

  Gate-In  → PreFatura ABERTA
  CRON     → atualiza provisão
  Gate-Out → PreFatura CONSOLIDADA → Fatura → Outbox EMITIR_NFSE_BOLETO
  Worker   → Faturamento mensal + NFS-e IPM + Boleto (real)

  TOS GATE_OUT_COMPLETED → emitir domain event interno → mesmo ArmazenagemBillingService
  (deprecar BillingOutboxProcessor hardcoded ou redirecionar para serviço unificado)
