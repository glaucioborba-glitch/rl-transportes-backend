NOTA METODOLÓGICA
-----------------
Foi realizada uma auditoria sistemática e automatizada do repositório (rotas,
controllers, páginas, módulos, fluxos de dados, builds e padrões de import).
Não é possível revisar literalmente "todas as linhas" de um monorepo deste
porte (milhares de arquivos TypeScript) em uma única passagem humana; esta
análise cobre 100% dos pontos de entrada (rotas HTTP, páginas Next.js,
módulos NestJS registrados) e amostragem profunda dos fluxos críticos
(Solicitações v2, Portal CX, Gate/Pátio, Agendamentos, Auth).

RESULTADO GERAL: O sistema é funcional e bem modularizado, com arquitetura
enterprise (observabilidade, HA TOS, portal corporativo, mobile hub, cockpit).
Há coerência na maior parte dos fluxos, porém existem duplicações históricas
(legacy vs v2), rotas colidentes e gaps de persistência que merecem correção
prioritária antes de produção em escala.

2. BACKEND — ROTAS E CONTROLLERS (93 controllers)
================================================================================

Prefixo global: NENHUM (rotas na raiz do host).
Guards globais: NENHUM — autenticação por controller/método.

2.1 PADRÕES DE AUTENTICAÇÃO
----------------------------
  Staff intranet:     AuthGuard('jwt') + RolesGuard + PermissionsGuard
  Portal CX:          CxPortalPublicApiForbidGuard + CxPortalAuthGuard +
                      CxPortalRateLimitGuard + CxPortalSegmentGuard +
                      PessoaPermissoesGuard
  Portal IAM público: POST /portal/login, register, etc. (sem guard)
  Mobile Hub v1:      MobileJwtAuthGuard + MobileRoleGuard
  Cockpit:            AuthGuard('jwt') + CockpitAccessGuard
  Plataforma B2B:     PlataformaIpAllowlistGuard + PlataformaPublicAuthGuard

2.2 PROBLEMAS CRÍTICOS DE ROTA
-------------------------------
[CRÍTICO] Colisão POST /v2/solicitacoes/:id/anexos
  - SolicitacoesV2Controller (staff JWT)
  - PortalSolicitacoesV2Controller (portal JWT)
  Nest registra ambos no mesmo path; o primeiro registrado prevalece.
  Risco: um público (staff ou portal) pode ficar inacessível ou com guard errado.

[ALTO] Três controllers no prefixo v2/solicitacoes:
  - modules/solicitacoes-v2/solicitacoes-v2.controller.ts (staff GET/DELETE/aprovar)
  - cx-portais/portal-solicitacoes-v2.controller.ts (portal POST)
  - pdf-operacional-v2/pdf-operacional-v2.controller.ts (PDF + verificação pública)
  Separados por verbo HTTP na maioria, exceto anexos acima.

[ALTO] Duas superfícies de portal cliente:
  - /portal/*           → PortalController (JWT corporate, Role.CLIENTE) — LEGACY
  - /cliente/portal/*   → PortalClienteController + DashboardPortalController — CX
  Sobreposição: solicitações, faturamento, boletos, NFSe com guards diferentes.

[MÉDIO] Duas stacks mobile:
  - /mobile/*           → MobileOperacionalController (legacy)
  - /mobile/v1/*        → MobileHubModule (moderno)
  Conceitos duplicados: gate, pátio, turno, operações.

[MÉDIO] Endpoints públicos sem auth (verificar intenção):
  - GET /metrics/cep-cache — métricas de cache CEP expostas
  - GET /api-contracts/v1/* — documentação de contratos pública
  - GET /v2/solicitacoes/:id/verificar — verificação QR (intencional)

[MÉDIO] Inconsistência de guards no portal:
  - DashboardPortalController usa JwtPortalAuthGuard
  - Demais controllers CX usam CxPortalAuthGuard (canônico)

[MÉDIO] Convenção de prefixos inconsistente:
  - v1/agendamentos, v2/solicitacoes, v2/gate, v2/patio
  - api/v1/* (integração)
  - Rotas sem versão: clientes, auth, faturamento, solicitacoes (v1 legacy)
  - CepCacheController usa @Controller('metrics') em vez de 'cep-cache'

2.3 MÓDULOS — WIRING
--------------------
  - Todos os 93 controllers estão registrados via feature modules em app.module.ts
  - HealthController declarado diretamente em AppModule
  - Nenhum controller órfão detectado na análise estática

4. FLUXO DE DADOS — SOLICITAÇÕES V2 (ANÁLISE DETALHADA)
================================================================================

4.1 MODELO DE DADOS (Prisma)
----------------------------
  Solicitacao (header) + filhos v2:
    TransporteSolicitacao, ContainerSolicitacao, AgendamentoSolicitacao,
    SolicitanteContato, SolicitacaoAnexo
  Operacional paralelo:
    AgendamentoTerminal (capacidade terminal, First/Last Mile, TOS)
    GateCheckIn/GateCheckOut, PatioUnidade (gate-v2)
    Container (TOS event-sourced)
  Legacy: Unidade, Portaria, Gate, Patio, Saida

4.2 FLUXO PORTAL → BACKEND
--------------------------
  1. Usuário escolhe intenção no dropdown (4 opções)
  2. Modal SolicitacaoFormModal envia POST /v2/solicitacoes/com-anexos
  3. Payload inclui tipoOperacao (intent enum):
       SOLICITAR_BAIXA
       SOLICITAR_IMPORTACAO_COLETA_DEPOT
       SOLICITAR_COLETA
       SOLICITAR_EXPORTACAO_ENTREGA_DEPOT
  4. Backend resolve via solicitacao-intent.util.ts:
       Baixa/Coleta     → FROTA_CLIENTE + motorista obrigatório
       Importação       → FROTA_FL + localOrigem + LS fixo
       Exportação       → FROTA_FL + localDestino + LS fixo
  5. Transaction cria Solicitacao + filhos v2
  6. Pós-transaction (best-effort): AgendamentosService.criar → AgendamentoTerminal

4.3 GAPS DE COERÊNCIA (ORDEM DE SEVERIDADE)
--------------------------------------------
[CRÍTICO] tipoOperacao (intent) NÃO É PERSISTIDO no banco
  - Perdido após create; impossível consultar/relatar por tipo de operação
  - Apenas inferível indiretamente via AgendamentoTerminal (se criado)

[CRÍTICO] AgendamentoTerminal é best-effort e só para 1º ISO
  - Falha silenciosa (logger.warn)
  - Rodotrem: segundo container sem slot terminal
  - Solicitação pode existir sem vaga no terminal/dispatch

[CRÍTICO] TOS Container desconectado do fluxo v2 portal
  - Gate-v2 opera ContainerSolicitacao/PatioUnidade
  - TOS Container exige AgendamentoTerminal — não é criado automaticamente no portal
  - Duas lifecycles de contêiner coexistem sem ponte

[CRÍTICO] TipoUnidade sempre IMPORT na criação v2
  - Incorreto para Baixa/Exportação/GATE_OUT
  - Corrompe métricas de dashboard (unidades.export/gateOut)

[ALTO] Dois modelos de agendamento sem leitura unificada no portal:
  - AgendamentoSolicitacao (sempre criado, exibido no portal)
  - AgendamentoTerminal (dispatch/TOS, não incluído nas APIs de listagem portal)

[ALTO] POST /cliente/portal/agendamentos bypassa intent
  - Cliente pode criar terminal row inconsistente com solicitação v2

[ALTO] tipoFluxo (TipoFluxoLogistico) nunca setado em v2
  - Legacy SolicitacoesService seta; v2 não

[ALTO] Máquina de estados fragmentada:
  - Legacy: PENDENTE → EM_ANALISE → APROVADO → EM_EXECUCAO → CONCLUIDO
  - v2 staff: → AGUARDANDO_GATE_IN (pula APROVADO)
  - Gate-v2: check-in de AGUARDANDO_GATE_IN ou APROVADO → EM_PATIO

[MÉDIO] Política de anexos inconsistente:
  - POST /v2/solicitacoes permite zero anexos
  - POST /v2/solicitacoes/com-anexos exige arquivos
  - aprovarStaff pode rejeitar por falta de anexo

[MÉDIO] Placeholder de transporte FL (00000000000, placas FLA0A00)
  - Gravado em TransporteSolicitacao para intents FROTA_FL
  - Pode confundir relatórios de motorista

[MÉDIO] Views SQL (vw_solicitacoes_v1_compat, vw_solicitacoes_legacy)
  - Não modeladas no Prisma
  - Labels desatualizados para AGUARDANDO_GATE_IN, EM_PATIO, etc.

================================================================================
10. CONCLUSÃO
================================================================================

O RL Transportes monorepo é um sistema enterprise maduro em evolução, com
múltiplas fases (portal CX, gate-v2, TOS HA, observabilidade, mobile hub,
cockpit, automação). A base compila no backend; o frontend tem 1 erro de
prerender. Os fluxos de Solicitações v2 e intent-driven UI estão implementados
e alinhados entre frontend e backend na camada de API, mas a persistência e
integração downstream (terminal, TOS, tipoFluxo, unidades) ainda apresentam
lacunas que podem causar inconsistência operacional no Dispatch Board e nos
KPIs.

Esta análise deve ser tratada como documento vivo — recomenda-se revisão após
cada sprint que toque portal, agendamentos ou TOS.
